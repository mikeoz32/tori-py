# ToriPy Microservices Application

This is a runnable application-level example, not a transport API snippet. It
contains four independent ToriPy processes:

- `catalog`: PostgreSQL-backed catalog RPC service with local CQRS.
- `orders`: PostgreSQL-backed order RPC service with local CQRS, catalog RPC
  calls, and an application-owned outbox relay.
- `notifications`: PostgreSQL-backed durable `order-created` event consumer with
  idempotent handling.
- `api-gateway`: HTTP-only Starlette application that calls the services through
  RabbitMQ RPC and owns no database.

The PostgreSQL container creates three databases with distinct login roles.
Each service has its own database URL, SQLAlchemy metadata, repository set, and
migration job. ORM rows and CQRS messages are never shared across service
boundaries; only the DTOs in `common/contracts.py` are shared.

`common/services.py` additionally declares the typed RPC Protocol contracts.
`ClientsModule` supplies one generic dynamic proxy through DI for each contract;
gateway controllers and the orders command handler call Protocol methods rather
than assembling RabbitMQ method names, payload dictionaries, or response types.

## Run The System

From the repository root:

```text
docker compose -f examples/tori_py/microservices_app/compose.yaml up --build
```

The gateway is available on the loopback interface at `http://localhost:8000`.
RabbitMQ management is at `http://localhost:15672` with `demo` / `demo`.

After the dependency-aware gateway readiness check passes, the complete
item/order/notification flow can be exercised with:

```text
uv run python -m examples.tori_py.microservices_app.smoke
```

Create a catalog item:

```text
curl -X POST http://localhost:8000/catalog/items -H "content-type: application/json" -d "{\"name\":\"Keyboard\",\"price_cents\":9900}"
```

Create an order using the returned item ID:

```text
curl -X POST http://localhost:8000/orders -H "content-type: application/json" -d "{\"item_id\":1,\"quantity\":2}"
```

Read the order and the notification generated by the RabbitMQ event:

```text
curl http://localhost:8000/orders/1
curl http://localhost:8000/notifications
```

Stop the stack and remove its databases with:

```text
docker compose -f examples/tori_py/microservices_app/compose.yaml down -v
```

## Tests

The application-root tests compile all four processes without opening broker
connections. The service package tests cover the underlying transport,
persistence lifecycle, and RabbitMQ contracts. The Compose stack is the real
PostgreSQL/RabbitMQ acceptance path.

```text
uv run pytest examples/tori_py/microservices_app -q
uv run ruff check examples/tori_py/microservices_app
uv run ty check examples/tori_py/microservices_app
```

CQRS is deliberately local to `catalog` and `orders`. RabbitMQ carries
validated integration payloads, not `tori-py-cqrs-core` command or query objects.
Delivery remains at least once: the orders outbox can publish duplicates and
the notifications consumer deduplicates by event ID. The example deliberately
does not implement business-command idempotency; that policy belongs to a real
application's request contract and persistence model.

Solitary repository and manager operations use `tori-py-sqlalchemy`'s automatic
transaction scope. Explicit transactions remain only where several database
operations must succeed together: order plus outbox persistence, event dedupe,
and outbox state changes.

HTTP inputs use ToriPy's existing `MsgspecValidationPipe`. RPC and event inputs
use typed `Payload()`/`Header()` annotations; the existing microservices binder
converts them with msgspec and rejects invalid messages before handler execution.
